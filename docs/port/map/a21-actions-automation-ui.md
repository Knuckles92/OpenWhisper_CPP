Area `a21-actions-automation-ui`. Paths are relative to `D:\coding\whisper_local` unless absolute. 13 files, 8337 lines, all read in full. The pure-logic service modules these pages sit on (`services/actions/model.py`, `services/automation/models.py`, `catalog.py`, `permissions.py`, `services/installed_agents.py`, `services/agent_mcp/setup.py`, `controls.py`, `services/actions/routing.py::status`) are NOT in this area, but I read them to pin the contract; they are summarised in "Data and formats" and "Dependencies on other areas". ## What the user gets

Three Settings pages in the "Automate" group plus one shared widget.

- **Actions** (Settings, Automate, Actions): what a hotkey, a spoken name, or the local API does with the words you say. Three stacked parts:
  - A purple-tinted featured **Agent hotkey** card: pick Claude Code / Codex / OpenCode (only ones a scan found are selectable), "Set it up", then capture a shortcut. Press once, speak, press again, and the coding agent opens a session (or answers quietly) with your words. Every change saves as it is made. Try it / Customize (opens full editor) / Remove.
  - **Your actions**: up to 50 saved actions as cards (icon, name, one-line summary, shortcut chip, "Say X" chip, on/off switch, Edit, Delete), an "Add action" gallery of 10 starting points (opens a link, agent session, quick answer, Claude Code channel, webhook, program, clipboard-only, scripts), and a full editor (name, kind-specific fields, how the words are prepared, shortcut, spoken names, what it is for, Try it, Save).
  - **Route by voice**: two switches (voice routing, also listen to normal dictations), a status line with an honest sentence and link to Fast judgments, a "Route by voice shortcut" field, and a privacy caption.
- **Hooks** (Settings, Automate, Hooks): three tiles, each a list with an inline editor under the row being edited: **Webhooks** (max 20; signed deliveries, test send, last 5 deliveries), **Programs** (max 20; run on events with event JSON on stdin; test run, last 5 runs), **Text filters** (max 10; an HTTP endpoint or program that changes words before or after AI cleanup; plus a read-only list of filters other programs registered through the live API with a countdown).
- **API & MCP** (Settings, Automate, API & MCP): the app-owned MCP server on/off bar with status, a Connection card (this computer vs another computer, copy address, setup prompt / Claude Code command / Cursor JSON / ChatGPT config with preview, masked access token with copy), Advanced connection (port, Tailscale), a Permissions card (read saved text included; rename dictations, rename meetings, read app preferences; per-preference write grants grouped in disclosures), then "Live events and automation": **Live API** (5 permission switches, address, endpoint list, curl example), **MCP Events** (preview; subscription count + Clear), **Claude Code channel** (research preview; `.mcp.json` entry and launch command). When a remote host is paired, a segmented "This computer / <host>" switch manages the host's MCP too, and a "share this computer's history through the paired host's MCP" tile sits on top.
- **Agent picker** (`AgentPicker` widget): four tiles (Claude Code, Codex, OpenCode, and "Pi" / "API / local model") with scan shimmer, found pills, install links, and a model row for the chosen agent. Embedded by the Models pages (AI cleanup, Meeting intelligence; those pages are other areas) and its scan seam is also used by `ui_qt/cleanup_agent_offer.py` and the Actions agent card.

## Platform-specific code

- Nothing in these files branches on `sys.platform`. Differences come from behaviors they name or call:
  - Agent surfaces: "Terminal" opens a new terminal window; "App" opens the agent's desktop app via a custom URL scheme (claude://, codex://). Terminal launching (Windows Terminal/cmd, macOS Terminal/iTerm, X11/Wayland/Hyprland terminals) is in `services/actions/launch.py` (not this area); the UI text is the same on all platforms. `OpenCode has no app` rule is platform independent.
  - "Choose a program" file dialogs: a Windows program is a `.exe`/script; on macOS/Linux any executable path; keep `QFileDialog::getOpenFileName` with no filter (as here).
  - Program paths shown by `basename`; `os.path.normpath` converts separators on Windows only.
  - Hotkey capture and display (`format_hotkey_display`, `ProfileHotkeyInput`, `CommandShortcutField`) come from the hotkeys area and are platform-specific (Win32 hooks vs evdev/Wayland portals); this area only calls their public API and must pause app hotkeys while capturing.
  - Tailscale access (MCP): a Tailscale interface is needed; the UI is the same everywhere, the address detection in `agent_mcp.runtime` is not here.
  - Monospace stack `"Cascadia Mono", "Consolas", "SF Mono", "Menlo", monospace`.
  - The Claude Code channel command line uses the interpreter or frozen exe path (`channel_command_line`); FioriVoce's C++ binary must provide its own `--channel` mode (open question).

### Risks
- Cross-thread widget lifetime: reproduce the session-lived relay pattern exactly (Python version had crashes from worker threads holding/deleting widgets). In C++ use a singleton QObject living on the GUI thread, emit queued signals with a token, never capture widget pointers in workers (use `QPointer` only to check on the GUI side).
- Dynamic-property styling: the QSS keys on `tone`, `state`, `checked`, `off`, `selected`, `searchHit`, `iconTone`, `tileId`, `kind`, `group`, `muted`, `found`, `missing`; every change needs unpolish/polish (`set_style_property`). Easy to lose a few; use the "Modules" lists as a checklist.
- Responsiveness: many widgets switch layout by their own width x font scale (Columns, ChipRow, AgentChooser, `_AdaptiveButtons`, `_TileGrid`, `_HookRow`, `ActionList`, gallery); tests pin fit at all scales. Port the thresholds as constants listed above.
- Custom painting of `AgentTile`/`StatusPill`/`AgentMark` must match (alpha values, easing, timings); QPainter is the same so a near line-by-line port is the safest path.
- Text fidelity: hundreds of exact strings (including curly quotes “ ”, the arrow U+2192 in "Open Settings → Meeting Mode → Fast judgments", "↗", "·", "…", "•", "π"). Keep UTF-8 source and a string-extraction check against the Python (grep) to avoid loss.
- JSON byte-compat for copied setup text (`json.dumps(indent=2, ensure_ascii=False)` key order and spacing); consider nlohmann::json `ordered_json`.
- Settings write semantics: `mutate_settings` must be atomic and the editor's `onto_saved` merge depends on it re-reading under the lock.
- Behavior of the full app is not exercised until the actions runtime, hooks engines, MCP server and agent scanner exist; much of the UI can be built and tested with fakes (the Python tests do this with `settings_manager` fakes).
- Remote-engine host tab and Route by voice are tied to undecided features.
- Route shortcut capture relies on the hotkey area exposing a "capture suspended" switch; check parity with `set_hotkey_capture_suspended`.

### Where native code can do better
- Startup: build the Actions/Hooks/MCP pages lazily as Python does (cheap in C++ too), and avoid constructing all 10 gallery tiles until the gallery is opened.
- Scans: run the agent scan (`--version`, auth probes) with `QProcess` in parallel (the Python used a 3-thread pool) and cache with a monotonic timestamp; start one scan at app start in the background so the cards are never in "Looking for…".
- Hooks live refresh polls every 1 s; connect to the engines' change signals instead of polling (keep a 1 s tick only for lease countdowns and elapsed text).
- `ActionList` and the hooks list can reuse row widgets rather than recreating cards (Python skipped rebuild only when the list was equal).
- Shared single `GuiRelay` and a typed token; avoids three separate relay implementations (action_relay, hooks `_EngineRelay`, picker `_ScanRelay`, MCP `_ServiceRelay`/`_LiveRelay`).
- MCP status/counters: replace the 500 ms polling with signals from the MCP runtime and event bus.
