# Remote engine UI: settings page, pairing dialog, host dashboard

Area a18. Files (all under `D:\coding\whisper_local`):
`ui_qt/dialogs/settings_remote.py` (1851 lines), `ui_qt/widgets/host_dashboard.py` (1794), `ui_qt/dialogs/pair_request_dialog.py` (227).
Everything here is the Qt face of `services/remote_asr/service.py::RemoteEngineService` (area a17). **The whole area is "undecided backend"** (remote-computer engine is not yet decided). Nothing in it is engine-specific to non-Parakeet engines, so if the remote engine is kept it ports as-is; if it is dropped the three files and their wiring go away together. The UI cannot be ported without the a17 service contract (listed under "Dependencies on other areas").

## What the user gets

1. **Settings -> Remote engine page** (page key `remote_engine`, heading "Remote engine", rail icon `server-blue.svg`). Heading blurb: "Transcribe dictation and meetings with another computer's engine over your network or Tailscale, or share this computer's engine with computers you pair." A two-tab segmented bar:
   - **Use another computer** (client): find a sharing computer on this network and the Tailscale tailnet (or type its address and code), pair with it (code, Tailscale auto-trust, or "ask the host's owner to Allow" with a matching 6-digit number on both screens), then "Use for dictation" / "Use for meetings", manage host models, rename or forget the host, choose where records are kept (This computer / Host / Both) and move records back and forth.
   - **Share this computer** (host): switch sharing on, see status/identity/reachability problems (firewall, VPN, public network) each with a fix button, toggles for what paired computers may do (manage models, keep records, manage MCP, Tailscale code-free pairing), port, "Show a pairing code", list of paired computers (rename, remove with keep/delete-records choice), and "Recover stored records...".
2. **Pairing request dialog** (`PairRequestDialog`): when a computer on the network asks to pair with this host, a modeless always-on-top "Pair a computer" dialog appears anywhere in the app (Settings open or not) with the asker's name/address, the 6-digit number, a countdown, what Allow grants, and Deny (default) / Allow. Closing it denies.
3. **Host Mode dashboard** (View -> Host Mode, Ctrl+Shift+H in main_window; window title "OpenWhisper Host"): a scrolling page replacing the recording tabs, for someone who runs the app only as a host. Hero card with animated server "beacon" and Start/Stop sharing; four stat tiles (Connected, Transcriptions, Audio transcribed, Speed); Engine card with model picker ("Serve"); Connected now (per-computer rows with animated link glyph); Paired computers (pairing code box, list); MCP card (on/off, copy token, copy agent prompt); Recent activity (12 lines, newest glow in). Links jump to Settings destinations.

- Service listener kinds the UI reacts to: `state`, `pair_request`, `activity`, `clients`, `engine`, `models`, `components`, `records`.
- Wire protocol (host/client) is owned by a17; this UI only touches: `protocol.DEFAULT_PORT=47821`, `MAX_NAME=60`, `format_sas` ("123 456"), `short_fingerprint` (first 5 blocks of 4 hex joined by "-"), `format_address` (IPv6 bracketed), `parse_address` (accepts scheme/path, `[v6]:port`, port 1-65535; error strings in protocol.py:311-355). These pure functions are golden-vector candidates.

## Engine-specific code

- **Drop:** nothing here exists only for other local engines. The `_engine_phrase` formatting ("Whisper turbo on cuda (int8_float32)") and the "streaming" detail ("live preview supported / no live preview") are generic over `describe()`.
- **Must adapt (Parakeet in-process):** host mode shares *the engine selected on this computer*, so the C++ `describe()` must report label (e.g. "Parakeet TDT 0.6B"), `device` ("cuda"/"cpu"), `compute_type` (may be empty; code handles both), `streaming` (false for Parakeet TDT: it is offline-only per CLAUDE.md, so the dashboard would show "no live preview"), `available`, and `status` text. `host_models()` lists ready (downloaded) models as `{family, model, label}`; with a single engine family this list is the installed Parakeet models only. `model_requested(family, model)` routes to the in-process engine switch and must run off the GUI thread (CLAUDE.md: never call the Recognizer from the GUI thread; engine reached through queued signals only). "Use for dictation" selects the `"Remote computer"` engine in the controller; OpenWhisper_CPP's engine selector needs that engine kind if the remote engine is kept.
- Client-side, a remote engine is a transcription *backend*, not Parakeet; it fits behind the same transcribe interface as the local engine.

## Porting notes

- **Decomposition.** Qt-free core (belongs with the a17 service in `src/engine` or a `src/remote` lib): formatting helpers above, `group_clients`, `event_text`, hero/state derivation (`HostViewModel`: state -> title/detail/tone), records-status line builder, pairing grants phrase, nearby-row detail builder. Qt layer (`src/app`): `RemoteEngineSection` (rename e.g. `RemoteEnginePage`), `PairRequestDialog`/`PairRequestPrompter`, `HostDashboard`, `HostBeacon`, `RemoteLinkGlyph`, relays. Keep the "no Qt in engine" rule; the view-models can be Qt-free and unit tested without a display.
- **Order of work.** (1) Decide whether the remote engine is kept; if so, a17 service contract and interfaces first (fake service for UI). (2) Pure helpers + golden tests. (3) `PairRequestDialog` + prompter (small, testable). (4) Settings page client tab (find/pair/paired/storage). (5) Host tab (share toggle, notes, toggles, port, devices, recovery). (6) `HostBeacon`/`RemoteLinkGlyph`/`StatusDot` painting. (7) `HostDashboard` and main-window Host Mode hookup. (8) MCP card last, after MCP (a20/a21) is decided.
- **Threading.** Reproduce the relay+token pattern: workers call `QMetaObject::invokeMethod`/emit queued signals on a session-lifetime `QObject`, receivers check a token or use `QPointer`; never hand a raw page pointer to a service listener. Never touch `Recognizer` from the GUI thread; `set_host_enabled`, scan, pair, and model listing must be off-thread.
- **Risks.** Large strings are the "same wording" contract (keep verbatim; consider one `strings` table). Dynamic properties and QSS selectors (`tone`, `state`, `busy`, `connected`, `tileId`, `buttonId`, `section`, `hostLink`) must be mirrored by the C++ theme. The settings page relies on shared tile widgets, `SegmentedBar` reflow and `_tile_group` from a11/a02, so the page cannot look right until those exist. Heavy dependence on a17 behaviours (Tailscale CLI, UDP discovery, TLS pinning, certificate fingerprint) which are the real cost of the feature; UI is only about a third of it. Qt on Windows: `WindowStaysOnTopHint` dialog may steal focus; keep Deny default.
- **Size.** Estimated C++: settings page 1,600-1,900 lines, dashboard 1,500-1,800, pair dialog 250-300, glyph/beacon painting 400, relays/view-model helpers 400-500: about 4,000-4,800 lines (Qt widgets are more verbose than PyQt). Plus ~300 for tests per module.
- **Native improvements.** Per-device records counts and `host_state()` (which asks Tailscale and enumerates the LAN address) can be cached/coalesced and moved off the UI thread (Python calls them inline in `refresh`); `QPainter` animations can share one animation clock instead of per-widget 33 ms timers; stat/relative-time redraw only needs a single 30 s timer; use `QSortFilterProxy`/model-view for the activity list and device list rather than rebuilding widgets, if the look permits; discovery and scan results can stream into the list as they arrive instead of waiting for the whole scan.
- **Open questions** (also in the structured summary): keep the remote engine at all; compatibility with OpenWhisper hosts/clients (wire protocol and pairing records); whether the dashboard's MCP card ships when MCP is undecided.
