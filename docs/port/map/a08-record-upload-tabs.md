## What the user gets

- **Quick Record tab.** An engine card (Backend, local engine fields, AI cleanup checkbox, Live preview checkbox, status dot and readout), an optional "Cleanup profile" card shown while AI cleanup is on, a column of Start Recording / Stop / Cancel buttons, a Command Mode hint under the buttons, then a collapsible "Transcription" card with a Fixed/Raw switch, a copy button that floats in the pane's top-right corner, and a stats strip. While recording, the transcript pane shows live preview text (when Live preview is on) with a trailing " ..." for the not-yet-final tail.
- **Upload File tab.** A dashed drop zone ("Drop audio files here") that also opens a file browser on click. One dropped file shows a file card (name, size, duration, sample-rate, Mono/Stereo, "One pass" or "About N chunks" chip). Two or more become a queue with per-row state badges (Reading / Queued / Working / Done / Failed / Stopped), move up/down, remove, per-row copy, and a "How these files relate" preset (Separate / Parts of one recording / Custom with a description dialog). Transcribe swaps the card footer for an inline progress panel (stage title, elapsed m:ss, Stop, determinate bar for batches, three-step stepper). When done the card shows "Transcribed in X · N.N× realtime · Cleaned in Y", then returns to actions after 1.4 s. Results render as Markdown in the transcript pane; an expand button opens a reading window with zoom, Fixed/Raw, and per-file pages for batches.
- **Scratchpad.** A small always-handy notepad (default 400x380, bottom-right of the screen) that autosaves to `scratchpad.txt`. Dictation inserts into it, spaced to fit the surrounding text, when it is visible and focused. Footer: word count, Transform menu (rewrite selection/all with a saved transform via the AI provider), Copy all, Clear with 8 s "Undo clear". Frameless rounded tool window with an "On top" toggle on classic desktops; a plain compositor-placed window on Wayland/Omarchy.
- **Compact controller.** In the compact main window a status line and three buttons (Record, Stop, Cancel).

## Porting notes

Suggested C++ decomposition:
- Qt-free core (`src/engine` or a new `src/core`, no Qt): `batch_upload.h/.cpp` (types and text helpers, UTF-8 `std::string`), `transcript_text.h` (transcript status classification: Error:/canceled/empty), `progress_model.h` (stage enum, step states, batch weights, elapsed format), `scratchpad_text.h` (`spaced`, `append_block` separator, word count, atomic-write helper, sequence-numbered saver logic). These carry the golden tests.
- Qt layer (`src/app`): `TranscriptionTabBase` (QWidget with virtual hooks `buildContentBeforeStatus/AfterStatus`), `TranscriptPane`, `QuickRecordTab`, `UploadFileTab` + `DropZoneWidget`/`FileInfoCard`/`UploadQueueWidget`/`UploadQueueRow`/`RelationPicker`, `TranscriptionProgressPanel`, `BatchRelationDialog`, `TranscriptViewerDialog` + `ReaderView`, `ScratchpadWindow`, `CompactRecordController`. Keep object names and dynamic properties identical so a ported `theme.qss` applies unchanged (needs the `@token` substitution step from the UI foundation area, plus a `set_style_property` equivalent that unpolish/polishes).
- Engine split: split the remote and API fields out of the base class into optional components so the first port ships Parakeet only; put an `EngineCard` widget with hooks (visibility of local/API/remote slots) between the tab base and tabs.

Order of work:
1. Core types + golden tests (batch_upload, scratchpad text rules, progress model).
2. `TranscriptPane`, base tab with local-only engine card and transcript/Fixed-Raw/collapse/stats.
3. `TranscriptionProgressPanel` and `DropZoneWidget`/queue widgets/`FileInfoCard` (can be developed with a fake job controller).
4. `UploadFileTab` lifecycle wired to the engine worker and batch runner (runtime area); relation dialog; viewer dialog.
5. `QuickRecordTab` and compact controller after the recording area lands (hotkeys, live preview).
6. Scratchpad (self-contained; needs focus_context and rewrite provider stubs).
7. Remote/API UI only if those backends are kept.

Risks and traps:
- Cross-thread delivery: Python used process-lifetime relays so deleted tabs are never referenced by workers (a crash fix pinned by tests). In C++ use `QPointer`/queued signals to a long-lived relay and check a token.
- UTF-16 offsets: Qt C++ already uses UTF-16 positions; do not re-implement the encode/slice hack, but test with emoji (test exists).
- Text edit sizing in `_QuickRecordTranscript` depends on document layout signals and style padding; reproduce `sizeHint` math (padding = widget height minus contents rect).
- `QTextDocument::setMarkdown` differs from the Python renderer (`render_markdown`, another area): headings (`## name`) and spacing must match the preview/reader styles.
- Stylesheet specificity quirks are documented in comments (drop zone child rules repeat ancestors; label background transparency; QSS replaced wholesale on `setStyleSheet`). Keep drop-zone styles as three full strings.
- Progress: terminal-state rule that a Canceled panel must not become Failed when the trailing "Error:" transcript arrives; `NONE` overlay state ends a job as failure; Stop must keep the tab locked until the terminal signal.
- `QueueItem.key` uses `normcase(abspath)`; on Windows that is case-insensitive, on Linux case-sensitive. Use `QDir::cleanPath` plus platform-appropriate case folding.
- Scratchpad window-flag changes recreate the native window (hides it); re-show manually. Wayland has no client-side positioning.
- Scratchpad hotkey focus rule (`isVisible && isActiveWindow`) must hold in the C++ dictation path, otherwise dictation lands in the wrong place.
- Strings contain OpenWhisper branding ("OpenWhisper couldn't read this file") and typographic characters (… · — ← → × −); decide OpenWhisper_CPP wording and keep UTF-8 in source (use `u8` or UTF-8 source encoding on MSVC with `/utf-8`).
- Settings compatibility: keep the same JSON keys if the C++ app should read an existing OpenWhisper install; otherwise document the divergence.

Rough C++ size: core 450-600 lines; base tab (local-only) 700-900 and +400-500 for remote/API if kept; QuickRecordTab 450; UploadFileTab with all widgets 1700-2000; progress panel 350; dialogs 650; scratchpad 700-800; compact controller 80. Total 5000-6500 lines (about 4000-4800 without remote/API).

Native advantages:
- Audio preview reads only headers (no full decode, no worker process) so queueing a large batch is instant; previews can be a thread pool of N rather than one worker per drop.
- `QSaveFile` for the Scratchpad makes the atomic write one call and the sequence-number saver can collapse to "write latest on a pool thread".
- The windowed live-preview text buffer and Markdown rendering are in-process with no marshalling; the status dot and detail label can bind directly to `EngineWorker` signals instead of string-matching status messages ("Ready", "Loading speech engine...").
- Faster startup: the whole tab scaffold, reader dialog and relation dialog can be constructed lazily (Python already creates the viewer and Scratchpad on first use; keep that).
- Batch jobs on Parakeet can report real per-file fractions rather than weights if the runtime exposes progress.
