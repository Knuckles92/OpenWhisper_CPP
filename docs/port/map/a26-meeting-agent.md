# Meeting agents: prompts, scheduler, tools, evidence, sidecar and installed-agent drivers

Source root: `D:\coding\whisper_local`. All paths below are relative to it.
Files in this area (8058 lines): `meeting/agent/{__init__,base,evidence,opencode_sidecar,openrouter_direct,pi_sidecar,prompts,scheduler,sidecar,tool_policy,tool_specs,typesafe_signals}.py`, `meeting/agent/installed/{__init__,acp,core,drivers,mcp_server}.py`, `services/meeting_agent_route.py`.

This area has **no Qt widgets**. Everything here is headless back-end logic: an "agent core" that turns transcript + dashboard state into validated state-patch ops, the scheduler that decides when to run it, and the transports to the LLM (Node sidecar, installed coding-agent CLIs). The dashboard that shows the results (cards, activity strip, finalization card) belongs to other areas; this area only produces the strings they show (progress/activity labels, outcome messages, error sentences).

## What the user gets

- **Live meeting intelligence.** While a meeting records (after a 2-minute warm-up), an AI "copilot" reads new transcript every 5-20 s (45-90 s for installed agents) and edits a shared dashboard: topic, rolling summary, key points, decisions, action items, risks, timeline beats, participant names, a quiet inbox of questions, and in-place ASR corrections of transcript lines. Every write cites transcript segment ids (`sg_...`) as evidence and is validated by the state-patch layer (another area).
- **A dedicated AI note taker** that keeps the `live_notes` card ("minutes") on its own cadence (every 2 card checkpoints or 45 s), with its own persona prompt.
- **Transcript polish passes** that only fix ASR text (every 6 checkpoints or 45 s; 15 s after the first fire).
- **Human guidance loop.** When a human corrects the transcript, writes a brief or a guidance note, the agent immediately re-reviews (guidance pass) even with no new speech, bypassing provider backoff once.
- **Explicit note requests** from the dashboard ("rewrite the notes as bullets…"), 1-4000 chars, max 4 queued, served on the same worker.
- **End-of-meeting**: optional final transcript polish over the whole recording in bounded blocks, then a blocking **consolidation** pass that finalizes the durable record (up to 900 s, 300 s silence limit), followed by deterministic state repair. User-visible outcomes: "Final insights are ready.", "Final insights timed out after 900s.", "Final insights failed: <error>", "AI insights are offline; final insights could not run.", etc.
- **Choice of agent**: packaged **Pi** (Node sidecar, default), packaged **OpenCode SDK** (Bun sidecar), or the user's installed **Claude Code**, **Codex**, or **OpenCode CLI**, locked down to OpenWhisper's meeting tools only (served over a loopback MCP server). Installed agents are also used for one-off tasks by other areas: custom reports, transcript cleanup, walkthrough write-ups (`run_agent_task`, `run_reading_task`, `run_viewing_task`).
- **Live activity strip** ticks ("Model is thinking through the transcript…", "Updating the dashboard…") and finalization progress text.
- **Health**: after 3 consecutive checkpoint failures intelligence is declared offline (transcript keeps recording); the Pi sidecar auto-restarts up to 3 times in 10 minutes.
- **Optional semantic topic-shift trigger and voice-command classification** through the TypeSafe "Jev" judge (prompt wording lives here).

## Platform-specific code

- Sidecar runtime: Windows prefers `<payload>/node.exe`, POSIX prefers `<payload>/node` and fails if not executable ("bundled node runtime is not executable: …"), else `node` on PATH (`sidecar.py:783-801`). Windows spawn uses `CREATE_NO_WINDOW` (`:889`).
- Installed agents: `popen_agent` puts Windows children in a Job object (suspended start, `CREATE_NO_WINDOW | CREATE_SUSPENDED`) and POSIX children in a new session; `kill_process_tree` kills the tree (Codex spawns helpers). Lives in `services/agent_process.py` / `services/installed_agents.py` (other area) but this area depends on it.
- Codex overrides are bare TOML-invalid literals so no quoting has to survive the Windows `.cmd` shim (`drivers.py:715`); `model_instructions_file` uses forward slashes.
- Claude Code `read_folder` must be a long path (`os.path.realpath`), as 8.3 short paths are refused (`core.py:394`).
- OpenCode SDK only on Windows x64, Linux x64/ARM64, macOS ("OpenCode runs on Windows x64, Linux x64/ARM64 and macOS only.").
- No X11/Wayland/Hyprland differences in this area.

## Engine-specific code

Nothing here depends on the speech engine; the agent consumes stored transcript segments. Notes for an in-process Parakeet engine:
- The scheduler's `engine` is the meeting engine (not the ASR engine). Its `clock.now_s()` (paused time excluded) drives warm-up and topic windows; the port must keep this clock in the meeting engine regardless of ASR.
- The 180 s refetch window and delivery ledger exist because mic and loopback chunks pass through one shared ASR FIFO and can commit out of start-time order (`scheduler.py:81-86`). A Parakeet engine on one worker thread has the same property; keep the ledger.
- Transcript polish and `revise_segment_text` correct Parakeet output just as they did Whisper output; nothing to drop.
- `openrouter_direct.py` is dropped (retired, not engine-related). Pi/OpenCode SDK sidecars depend on Node/Bun payloads and a cloud/own text endpoint: undecided.

## Porting notes

**Decomposition.**
- Qt-free core library (`src/meeting/agent`, plain C++20, nlohmann `ordered_json`):
  - `prompts` (strings as raw literals, builders), `spotlight`, `evidence` (+ `difflib` port), `tool_specs`, `tool_policy`, `progress_labels`, `route`.
  - `scheduler` with an injected clock, an `IMeetingHost` interface (transcript fetch, delivery ledger, snapshot, revoke writes, meeting clock), and an `IAgentCore` interface; one worker `std::jthread` + condition variable; keep `run_due()` public for deterministic replay tests.
  - `agent_core.h` interfaces mirroring `AgentCore`/`AgentToolHost`; `AgentResult`, `OpResult`, `CheckpointPayload`.
  - `jsonrpc_stdio` (shared by sidecar and ACP): line framing, pending map, timeout + stall waits, cancel.
- Platform/Qt layer: process spawning and tree kill (`QProcess` + Windows Job object), loopback MCP server (`QHttpServer` or a `QTcpServer` HTTP subset), installed-agent drivers (Claude, Codex, OpenCode ACP), Node/Bun sidecar supervisor if kept.

**Order of work.** (1) interfaces + prompts + spotlight + evidence + tool specs/policy with golden vectors; (2) scheduler with fake host/agent, replaying `test_meeting_scheduler`/`live_agent_workflow` traces; (3) MCP server + tool contract; (4) Claude Code and Codex headless drivers; (5) OpenCode ACP driver; (6) installed core + `run_*_task`; (7) Pi sidecar supervisor (if kept); (8) OpenCode SDK sidecar (if kept); (9) TypeSafe signals (if kept).

**Rough size.** prompts ~750, spotlight/render ~250, evidence+difflib ~250, tool specs/policy ~350, scheduler ~1000, JSON-RPC stdio + ACP ~500, MCP server ~400, drivers ~1000, installed core ~350, route/factory ~150, Pi sidecar ~1000, OpenCode SDK ~150, typesafe ~80. About 5,000 without sidecars, ~6,200 with.

**Risks.**
- JSON key order: `QJsonObject` sorts keys, which changes spotlight order, participant rendering and card iteration. Use an insertion-ordered JSON type end to end.
- Exact prompt text is benchmarked behaviour; any whitespace drift changes model output. Diff against Python output byte for byte (including Python float `str()` for `start_s`, `:g`, `:.1f`, `:.2f`, code-point truncation, `json.dumps` ASCII escaping and separators in tool results).
- difflib parity for evidence repair (ratio, `get_close_matches` ordering).
- Concurrency: cancel vs tool-call authority (`_tool_authority_lock`, endpoint lock, per-pass cancel event), stale restart generations, the reader thread never blocking on tool work. These guard against late writes into durable state.
- External CLI flags and event formats drift (Claude Code, Codex, OpenCode versions); keep feature detection from `--help` and tests with fake CLIs.
- Keeping Pi/OpenCode SDK means shipping and updating a Node/Bun payload and the TypeScript sidecar; the protocol tokens and env names must stay compatible.

**Where native code helps.** No interpreter start for the sidecar supervisor and drivers; the MCP server and JSON-RPC loops cost less memory than Python threads; prompts can be built straight from the in-memory state without the `to_dict()` snapshot copy. The Python code works around the GIL in places (single tool worker so the reader can answer pings); in C++ the reader stays responsive without that, but keep a single serialized tool queue because ordering is part of the contract.

**Deliberate differences to decide.** Product name in prompts and tool contract ("OpenWhisper", MCP server name `openwhisper`, tool prefixes `mcp__openwhisper__`, `openwhisper_`), env var names, temp folder names. Changing the MCP server name changes the tool prefixes the model is told to call; change them together.
