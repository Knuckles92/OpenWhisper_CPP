# Meeting Mode Qt UI: tab, past meetings, consent/setup/recovery dialogs, meeting settings pages

Area a31-meeting-qt-ui. Source root `D:\coding\whisper_local` (read-only). 16 files, 6535 lines, all read in full. Paths below are relative to that root.

## What the user gets

Meeting Mode is the last main-window tab. It is a two-pane "studio": a 320 px control column on the left and a stage on the right.

- Column: title "Meeting Mode" with a "Beta" tag, a Start Meeting button (or Open dashboard / Copy guest link while live), a one-line speech destination note, an "AI INSIGHTS" section (switch, model line, "Change..." link), an optional "Meeting brief" text box, and a "Meeting setup ->" link.
- Stage, three states: **empty** (what Meeting Mode does, three numbered steps, platform note, the 3 newest past meetings), **live** (on-air card with breathing red dot, status pill, big elapsed clock, Pause/Resume and End), **result** (finalization card: meeting identity, step checklist with progress bar, Retry / Run again / Re-run speakers / Open report / Continue in background / Keep for later / Done).
- Past Meetings sidebar panel: searchable list of up to 100 meeting cards (title, date, preview, duration, insight pill, location pill), right-click menu (Copy transcript, Show in Folder, Delete), header menu (Refresh, Export, Open meetings folder, Clear history, Clear history + recordings), calendar button, and meetings kept on a paired host merged in.
- Modal dialogs: first-visit intro, unsupported-platform / Linux-preview notice, first-run setup (model check + 6 s audio check), macOS Screen Recording permission, Linux system-audio remediation, AI-insights consent, OpenAI system-audio-upload consent, delete confirmation, bulk export, crash-recovery list.
- Two Settings pages inside the Meeting Mode settings group: "After End" (re-decode, polish, final report, experimental insight review, report views) and "Fast judgments" (judge route, key notice, route test, feature switches).
- Two service modules: model/audio readiness checks for the setup dialog, and the shared re-run options used by desktop Retry, dashboard re-run and crash recovery.

## Porting notes

### Suggested C++ decomposition
Qt-free core (`src/engine`-style, or a new `src/core`; no Qt):
- `meeting_format.h/.cpp`: date/duration/identity-meta formatting, elapsed-clock formatting, title fallback, preview text (uses ISO parsing; a28/a29 shared).
- `finalization_view.h/.cpp`: decode the finalization payload and compute the card view model (title, message, tone, per-button visibility, steps, progress). This is the main golden-vector target.
- `meeting_setup.h/.cpp`: `ModelSetup`, `AudioCheck`, `InspectModels`, `PrepareModels`, `CheckAudio` with a `cancel` atomic and a progress callback; depends on an audio-capture interface (a05).
- `meeting_rerun.h/.cpp`: option building and speaker gate (only if cloud kept).
- `consent_copy.h/.cpp`, `ai_destination.h/.cpp`: string builders from a settings struct.
- `past_meetings_model.h/.cpp`: list filtering, count/placeholder text, merge/sort with host list, pill derivation.

Qt layer (`src/app/meeting/`, camelCase):
- `MeetingModeTab` (+ `LiveDot`, `RecentMeetingRow`, `BriefEdit`, `FinalizationCard` split out of the 2188-line Python class), `PastMeetingsPanel` + `PastMeetingItem`, one class per dialog, two settings section classes taking `std::function` callbacks like the Python.
- Prefer a `QAbstractListModel` + delegate only if profiling shows card widgets are slow at 100 rows; otherwise keep card widgets and `reconcile_cards` equivalent (compare fingerprint, reuse).
- Use signals exactly as named so a03 controller wiring ports 1:1.

### Order of work
1. Core formatters and finalization view model with golden vectors (no UI).
2. Past meetings panel + card (needs repository from a28 or a stub provider like the Python test seam).
3. Meeting tab: column, empty stage, live card (clock), then finalization card.
4. Dialogs in this order: delete, recovery, intro, consent (both), setup (+ meeting_setup core), export subclass, settings After End, settings Fast judgments (last; backend-dependent). Platform dialogs (unsupported, mac permission, Linux audio) only when those platforms are targeted.
5. Theme QSS block for Meeting Mode (theme.qss lines 2700-3460) copied with token substitution; verify against screenshots of the Python app.

### Risks
- Visual fidelity: the stylesheet relies on dynamic properties (`tone`, `finalizationTone`, `selected`, `pillTone`, `meetingLink`, `meetingResultAction`, `buttonId`) and a repolish step after change; the C++ port must call `style()->unpolish/polish` (the Python `set_style_property` / `repolish` helpers).
- Font scale (`scaled()`) must be implemented in the foundation before the tab (a02), else column/on-air sizes drift.
- Many strings carry typographic characters (…, —, →, ·, ✓ ● ✗ – ○, curly quotes, "≥"): keep UTF-8 source and `QStringLiteral(u"...")` / `u8` literals; do not retype.
- Threading: three different relay patterns (recent, fetch, probe, route verify, export). Unify into one reusable "result mailbox + token" helper; never emit from a worker on a dialog that can be destroyed (the Python comments record real crashes).
- Close-while-checking: the setup dialog must not return until capture devices are released (WASAPI exclusive/loopback handles); enforce in C++ with RAII stop plus a deferred `done()`.
- Meeting payload shape is defined by a03/a24; confirm field names with those maps before writing `set_meeting_state`.
- Scope creep: A31-31 (host sync) and A31-44 (Fast judgments) pull in large undecided backends; stub behind interfaces.

### Rough C++ size
Core ~1,300 lines; Qt tab ~1,900; past meetings ~900; dialogs ~1,900 (setup 350, platform dialogs 700 if included, consent/intro/recovery/delete/export 700, settings sections 700); total about 6,000-7,500 lines (the Python is 6,535 and Qt C++ is more verbose, but Windows-only and Parakeet-only trims roughly 1,000).

### Native opportunities
- Setup progress arrives by queued signal instead of an 80 ms poll timer; the audio check can run its mic and loopback streams on the native audio thread with a lock-free RMS meter, finishing as soon as both see signal (already early-exit, but with no 100 ms polling latency).
- Model readiness is a file stat and a runtime `dlopen` check; no Hugging Face client, so "Download missing files" may collapse to opening the model folder or invoking the app's own downloader.
- Cards and recent list read from SQLite directly on a worker thread; avoid per-meeting `get_meeting_content_summary` calls (use one aggregate query like `list_past_meeting_summaries`).
- Lazy page construction (Settings sections use `ensure_built`) matters less in C++ but keep it for startup.
- LiveDot can use a `QVariantAnimation` (one timer, stops when hidden) instead of 50 ms manual ticks.
