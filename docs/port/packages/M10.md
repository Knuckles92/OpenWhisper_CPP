# M10 Native updater and parity sweep: work packages

Binding scope of packages M10.1 to M10.28 (architecture amendment 7). Names of targets,
directories, classes and headers come from `docs/port/ARCHITECTURE.md` and are not changed here,
except where "Changes to the cut" says so. Python paths are relative to `D:\coding\whisper_local`
(OpenWhisper 2.8.92, commit `768b559edd93`). Area maps are in `docs/port/map/`. M0.1 to M0.12,
M1.1 to M1.7, M1.10 to M1.13, M1.17 to M1.19 and M1.22 are merged, and their headers are the
contracts as built; every other package of M1 to M9 is planned against its spec in
`docs/port/packages/M<n>.md`. Where a merged header differs from a spec, the M10 package follows
the header and says so in its report (amendment 12).

## Overview

M10 is the last milestone. It ports the transactional native updater of a16 (prepare a verified
update archive beside the install, swap directories after the app quits, start the new version
for a health check, roll back files, data and registration when it fails, recover after a crash)
as the Qt-free library `fv_update_native` and the executable `fiorivoce-updater`; finishes a34
(the update archive, the updater in the installer, the setup helper protocol, the release
workflows that draft or upload a release, written and never run); measures performance budgets
(startup, memory, time from key to text, agent-loop time to first token and pass latency) against
OpenWhisper's own numbers; lands everything earlier milestones pushed out (benchmarks, native
gains, open items, the gaps of `fv_pyport`); and sweeps every area for parity, so that
`docs/port/parity-report.md` shows 100 % of the kept features and `docs/port/differences.md` lists
every deliberate difference from OpenWhisper.

**Demo (section 11):** "A signed release updates itself, rolls back after a forced failure, and
passes the health gate." There is no signing certificate (amendment 16), so the release is
unsigned and the signing steps are written and skipped. The update source stays `none` until a
public FioriVoce repository exists, and no worker installs, relaunches the app or changes system
settings, so the demo is proven in two ways:

1. **By the workers, on this machine** (M10.17, `tests/updater/test_m10_demo.cpp`, `[platform]`):
   a 0.1.0 install tree in a temporary folder (a small fake `fiorivoce.exe` built by the tests,
   the real `fiorivoce-updater.exe` with its DLLs, Inno uninstaller stand-ins), registered under
   a test registry key, checks a loopback feed, downloads `FioriVoce-0.1.1-win64.zip`, prepares
   the candidate, hands off to the staged updater and exits; the updater swaps the trees, starts
   the new fake app with `--update-health`, which acknowledges, and the install reads 0.1.1 with
   its registration updated and the transaction cleaned up. A second release 0.1.2 whose fake app
   exits 1 in its health launch is rolled back: files, settings file, database and registration
   are back to 0.1.1, `apply_error.txt` holds the reason, and the old app is started again. The
   test's journal names a test app id (every mutex name derives from it) and test registry keys
   for the registration and the RunOnce value (change 6), the data root of every process comes
   from `FIORIVOCE_DATA_DIR`, the updater writes its failure message to a file instead of a
   window (change 6), and nothing outside the temporary folders and the test keys changes.
2. **By the owner** (steps in `packaging/windows/README.md`, written by M10.17): the real
   installed FioriVoce 0.1.0 updates itself to a 0.1.1 build served by
   `tools/release/serve_update_feed.py --archive`, then a 0.1.2 build made to fail its health
   launch (`FIORIVOCE_TEST_FAIL_HEALTH=1` set by the owner in the 0.1.2 build's environment, see
   M10.12) rolls back to 0.1.1.

**Rules that apply to every package below** (M0.md to M9.md's rules, unchanged):

- A package changes only what its `Owns` line lists, plus its own `tests/<dir>/PARITY.json`
  entries, its case files `tools/parity/cases/<python.module>.py`, its builder file and its
  `tests/golden/<python.module>.json` and `tests/reference/<widget>/` entries.
- Function-level PARITY: statuses `ported`, `golden`, `dropped`, `other-platform` (added by M10.2)
  and, only in packages of waves 1 to 4, `pending` with a finishing M10 package. Nothing is
  pending after M10.25.
- Qt-free code keeps Python's names in snake_case; Qt classes use camelCase (section 8.3). Every
  class states its affinity. User-visible strings are copied verbatim from the cited Python line;
  "OpenWhisper" in copy becomes `identity().product`; `lint.brand` allows the literal only in
  `base/identity.cpp`, `backup/import*`, `remote/wire.h` and tests.
- Code that takes over the desktop session (message boxes, the real RunOnce key, the real app
  mutexes against a running FioriVoce, starting the real app, hooks, clipboard, devices) is
  proven through fakes; the real-API test is tagged `[interactive]`, written and not run
  (amendment 14). File, child-process, named-mutex-under-a-test-name and
  registry-under-`HKCU\Software\FioriVoceTest\` tests are `[platform]` and run.
- No worker runs a setup program, installs or uninstalls anything, changes system settings, writes
  the real `RunOnce` key or the real uninstall key, or starts `fiorivoce.exe`. No test, tool or
  generator contacts the network beyond 127.0.0.1. Nothing pushes, publishes or uploads.
- Python for vectors and reference measurements is OpenWhisper's 3.12 interpreter through
  `tools/parity/ow_isolation.py`, read-only (amendment 13); never git or any write inside the
  OpenWhisper checkout.
- Format with `wsl clang-format --dry-run -Werror` (amendment 3). PowerShell, Inno, YAML and
  Python files are not clang-formatted. Scratch files go in the worktree's own `out/` folder
  (amendment 17).

## Changes to the cut

Section 11 gives M10 no package table; these choices are this spec's.

1. **A new core library `fv_update_native` (`src/update_native`)** holds the transaction: names,
   journal, manifest and topology, archive reading and verified extraction, data snapshot,
   compatibility files, prepare, commit, rollback, recovery, pruning, the health protocol and the
   setup helper protocol, behind a `NativePlatform` interface. `fv_update` (M3) keeps the feed,
   check, download, runtime and gates, implements `NativePlatform` for Windows and gains
   `DEPS fv_update_native`. The a16 map's porting notes name this split (`fv_update_native`);
   splitting lets two packages work on the updater in one wave.
2. **The update archive is a Zip64 deflate `.zip`**, `FioriVoce-<version>-win64.zip`, read with
   `archive::ZipReader` (M1.7) and written with `archive::ZipWriter` (M3.1), not a `tar.xz`:
   `vcpkg.json` is frozen and has no liblzma. Every member rule of `safe_extract_tar_xz` is kept;
   a zip has no hard links, so `test_rejects_hardlink` is dropped.
3. **`fiorivoce-updater` uses the dynamic CRT and the vcpkg DLLs like the other executables**,
   not a static CRT (section 2.3): every `fv_*` library is built `/MD`, so a `/MT` updater could
   link none of them. Because the updater must run outside the install folder, `prepare` copies
   it into the transaction folder together with the DLLs it imports from the install folder,
   found by a small PE import reader (`update_native/pe_imports.h`). The installer extracts the
   same closure for the setup helper.
4. **Packing is C++**, not a Python script: `fiorivoce-updater --write-manifest`,
   `--pack-archive` and `--verify-archive` call the same `build_update_manifest`, topology and
   verification the app uses, so there is one definition of the manifest
   (`scripts/pack_update_archive.py` is ported there).
5. **FioriVoce's topology replaces `_internal/`:** the managed top-level names are
   `fiorivoce.exe`, `fiorivoce-cli.exe`, `fiorivoce-updater.exe`, `*.dll`,
   `THIRD_PARTY_NOTICES.md`, the manifest and sentinel, and the directories `platforms`, `styles`,
   `imageformats`, `iconengines`, `tls`, `networkinformation`, `generic`, `licenses`, `webui`
   (M3.11's `stage.ps1` layout plus M7's `webui`). Only Inno's `unins\d+\.(exe|dat|msg)` are
   preserved. The `_internal/nvidia` preservation is dropped (engine-specific).
6. **The journal binds its registration, recovery keys and app id:** besides OpenWhisper's fields
   it stores `registration` (`hive`, `key_path`, `view`), `runonce_key` and `app_id` (braced
   GUID), and drops `nvidia_preserved`. The updater therefore needs no override switch for tests:
   the demo test's journal names test keys and a test app id. Validation accepts only `HKCU` and
   key paths under `Software\`; the RunOnce key must be
   `Software\Microsoft\Windows\CurrentVersion\RunOnce` or lie under `Software\FioriVoceTest\`;
   `app_id` must equal the release identity's unless the registration lies under
   `Software\FioriVoceTest\`, and only then does the updater derive its mutex names from the
   journal's `app_id` (`names_for`) and run quiet: `NativePlatform::message_box` logs the text at
   WARNING and appends it to `<updates root>/message_box.txt` instead of showing a window, so the
   `[platform]` demo never puts a dialog on the desktop. FioriVoce has no legacy journals, so
   `cleanup_rollback` is required.
7. **No restart dance for the helper:** a native executable is one process, so leaving the launch
   folder is a change of directory (`leave_launch_directory`'s first half); the onefile
   bootloader restart is dropped with its three tests.
8. **The setup helper protocol is reinstated** (A16-23): `FioriVoce.iss` calls
   `fiorivoce-updater --setup-action prepare|finish|rollback` as OpenWhisper's `RunSetupHelper`
   does, and M3.11's `[InstallDelete]` list is removed in favour of it.
9. **The bridge floor is FioriVoce's first release that ships the updater** (lead decision 2),
   not 2.5.2: a release at or below the floor and any archive whose `minimum_updater_version` is
   above the running updater must use the setup.
10. **Benchmarks get a Qt-free library `fv_bench` (`src/bench`, `KIND core`) and a developer
    executable `fiorivoce-bench` (`src/bench_cli`, `KIND exe`, `main.cpp` only, never staged or
    installed).** The live-preview, cleanup-levels, meeting-accuracy and local-ASR harnesses that
    measure FioriVoce's own behaviour are ported into the library, so `tests/bench` can link them
    (a test cannot link an `exe` module's sources; `tests/cli` runs its executable as a child for
    that reason); the meeting product eval and the audio-DSP denoiser benchmark are dropped (lead
    decision 7). For the same reason the updater's logic (`run_updater`, the launch folder,
    `updater.log`) lives in `fv_update_native` and `src/updater` holds only `main.cpp` and the
    version resource (M10.11).
11. **Performance tests live in `tests/perf` with the CTest label `perf`**, which the default
    presets exclude (lead decision 3); they record numbers and never fail on a budget. Budgets are
    checked by `tools/perf/check_budgets.py` and every miss names the sweep package that fixes it.
12. **The parity sweep owns directories, not areas.** Each sweep package walks the inventories of
    its areas (and of its `a32` checklist sections) and fixes inside its own directories; a fix
    needed elsewhere is handed off to a sweep package of a later wave or to M10.25, which runs
    alone in the last wave and may change any directory for handed-off fixes. M10.10 owns the two
    small foundation additions history needs (`EventSink::clear_replay`, `pyport::py_repr`) in
    wave 2, ahead of the shell sweep.
13. **Three sweeps split by directory** (the first cut gave each one worker more than 200 IDs
    plus fixes): audio and speech (M10.7) apart from models and downloads (M10.26), the
    controller and dictation (M10.19) apart from the Quick Record and Upload File tabs (M10.27),
    the meeting engine (M10.21) apart from the dashboard server and the meeting Qt UI (M10.28).
    Each half owns its own directories and audit files; an ID one half finds in the other half's
    directory is handed off as the sweep protocol says.

## The parity sweep

### Grouping and order

The 34 areas are grouped so that each sweep package owns a disjoint set of source directories
(table "Every other ID" above and the Owns lines). Order: the leaf and core directories first
(wave 2: audio and speech; models and downloads; text AI; input and overlay; history, settings
and data), so
that the integrating layers are swept on fixed foundations; the services with their own pages next
(wave 3: automation and agents, remote, walkthroughs, meeting capture and state) beside the
updater integration; the integrating layers last (wave 4: shell and foundation, controller and
dictation, record tabs, Settings dialog, meeting engine, meeting UI and dashboard, meeting
intelligence, actions UI), after the updater has
changed `ui_shell`, `app` and `ui_controller`; and in wave 5 M10.25 sweeps a16, a33 and a34,
resolves every handoff and generates the reports.

### Sweep protocol (every sweep package follows it)

1. **Inputs.** The inventories ("Feature inventory" and "Added by check") of its areas, its a32
   lines, the earlier specs' Scope tables (they say where each ID's C++ lives), the
   `PARITY.json` of its test directories, `docs/port/performance-report.md` (budget misses
   naming it), the items of "Items pushed to M10" naming it, and every `handoff` addressed to it
   in earlier audit files.
2. **Walk every ID.** Find its C++ (the spec's Scope row first, then a search). Mark it:
   - `verified`: the C++ exists and a test pins the behaviour (a ported test, a golden vector, a
     reference screenshot, or a test this package adds that cites the map row);
   - `fixed`: the behaviour differed, the package fixed it inside its directories and added or
     corrected the test;
   - `difference`: a deliberate difference, with the decision that made it (architecture section,
     amendment, a spec's "Changes to the cut" item, or a lead decision of this spec);
   - `dropped` (engine-specific or Python plumbing, with the earlier spec's reason) or
     `other-platform` (with the platform);
   - `handoff`: a fix is needed in a directory the package does not own; name the package (a sweep
     package of a later wave from the order above, else M10.25) and what to change.
   The Python is read only where no test covers an ID, a test fails, or the map is not precise.
3. **Close the test ledger.** Every function of every OpenWhisper test file in its
   `PARITY.json` files is listed; nothing stays `pending`; a function left pending by a package
   that never finished it is ported now.
4. **Screenshots.** Every reference test of its directories passes at 0 differing pixels, or
   carries a `.tolerance.json` (`max_differing_pixels`, `max_channel_delta`, `reason`) with the
   measured difference (amendment 5), listed in the report for the lead.
5. **Desktop takeover.** Every real-API path of its directories has its `[interactive]` test
   written; none is run.
6. **Budgets.** Fix the misses `tools/perf/budgets.json` assigns to it; re-run the metric with
   `python tools/perf/run_perf.py --metric <name>` and record before and after.
7. **Audit files.** Write `docs/port/audit/<area>[-<package>].json` for each area it walks (schema
   in M10.2) and run `python -I -B tools/parity/feature_audit.py --areas <its areas>` and
   `python -I -B tools/parity/parity_report.py --check`.
8. **Limits.** A fix over about 300 lines, or one that changes a member another package already
   codes against, is not made inside the sweep: it becomes a `handoff` to M10.25 with "interface
   fix" in its note, and the report says so.

### What a sweep package reports

Its package report has these sections: counts per area (verified, fixed, difference, dropped,
other-platform, handoff); every fix (ID, files, test); every difference added (ID, one sentence,
source); tolerance files added with their numbers; `[interactive]` tests written and not run;
budget misses fixed with before and after numbers; open items closed; handoffs issued. The
ledger itself is the audit files and the `PARITY.json` files; `docs/port/parity-report.md`,
`docs/port/differences.md` and `docs/port/performance-report.md` are generated by M10.25 from
them (M10.2 and M10.3 write the generators) and are, with the final package report, the
milestone's deliverables.

### Traps

- Member names are checked before any path is built: no `\`, no rooted, drive, UNC or `:` names,
  no empty, `.` or `..` parts, no trailing space or dot, no reserved names (stem before the first
  `.` upper-cased against CON, PRN, AUX, NUL, COM1-9, LPT1-9), no control characters, at most 240
  characters and 20 parts (`app_update_apply.py:480-525`).
- Extraction writes only members the manifest authorises with exactly the declared size, refuses
  case-insensitive duplicates, directories other than implied ones, links and anything not a
  regular file, caps members at 50,000 and the unpacked total at 2 GiB plus 4 MiB for the manifest
  (`app_update_apply.py:769-903`); the root manifest is read without enumerating the whole archive
  and must equal the extracted copy.
- `member_count` is files plus one (the manifest); `unpacked_bytes` must equal the sum of sizes;
  a schema or topology revision mismatch raises `UpdateRequiresSetup` ("This update changes the
  install layout and must use the installer."), the wrong product or app id "The update package
  is not for FioriVoce." (`app_update_apply.py:623-698`).
- File operations retry on sharing violations and access denials for 60 s, polling every 0.25 s,
  and never retry other errors (`app_update_apply.py:295-305`); hashing the app that just exited
  waits for its image handle.
- The snapshot uses the SQLite backup API so committed WAL pages are included; restore verifies
  every digest first, removes `-wal` and `-shm`, writes through a `.update-restore` temporary and
  a write-through replace, and restores an absent file as absent (`update_data.py:18-90`).
- `reject_reparse_chain` walks from the path up to its root and refuses any junction or symbolic
  link on the way (`app_update_apply.py:445-479`).

### Traps

- Every transition writes the journal first and is idempotent; the RunOnce value is set before

- Never overwrite an existing `.failed-<id8>` or rollback tree (`_restore_rollback`, 2519;
  `_check_install_unchanged`, 2813); a foreign executable installed during recovery makes the
  transaction `superseded`, not rolled back (`_reconcile_interrupted_commit`, 2950-3003).
- An empty health file is not success; the health wait ends at once when the new process exits
  (`_wait_for_health`, 2263-2289); after health is confirmed a failure only records "The new
  version is running, but update finalization failed: <reason>" and data are never rewound.
- Cancel is honoured after extraction and again after hashing (`prepare_candidate`, 1427).
- `prepare_candidate` writes the context's `app_id`, the request's registration and RunOnce key
  into the journal (change 6); commit and recovery re-check them through `validate_journal_binding`.
- A registered `DisplayVersion` that differs from the running version only logs a warning; the
  commit repairs it (`test_stale_registered_version_is_repaired_by_native_update`).

## Contract gaps (each has an owner above; none needs an interface-fix package)

1. **`update_native::NativePlatform`, `TxnContext`, `UpdateJournal` and the transaction API** do
   not exist: M10.1 and M10.5 add them in the new `fv_update_native`.
2. **`update::ReleaseIdentity` has no `updater_exe`; `archive_asset_name` names a `.tar.xz`**:
   M10.6 adds the key to `data/release_identity.json` (M3.3's tools ignore unknown keys) and makes
   the archive `FioriVoce-<ver>-win64.zip`.
3. **`update::InstallProbe` lacks the full registration** (`UninstallString`, `EstimatedSize`,
   `InstallDate`, view, hive): M10.6.
4. **`update::MutexApi` has no timed acquire**: M10.6 adds `acquire(name, timeout)`.
5. **`process/detached.h` keeps no handle**, but the updater waits on the new app and terminates
   it: M10.6's `LaunchedProcess` in `update/win/launch.cpp` (not in `src/process`).
6. **`update::Handoff` has no native result; `UpdaterRuntime::discard_handoff` cannot abandon a
   transaction**: M10.12.
7. **`Bootstrap` has no health-launch option**: M10.12 adds `StartupOptions::update_health_token`.
8. **`EventSink::clear_replay()`** and **`pyport::py_repr`**: M10.10.
9. **`pyport` has no `re.ASCII`**: M10.18 adds the flag.
10. **`audio::WavWriter` has no stamp-failure seam; no bext originator reader**: M10.7.
11. **`engine::RequestOptions` has no speech contexts**: M10.24.
12. **`llm::StreamError` keeps no provider message**: M10.22.
13. **`UpdateJournal` has no app id, and `NativePlatform::message_box` cannot be silenced** (the
    demo would show a window from a `[platform]` test): M10.1 adds `app_id` and `is_test_journal`,
    M10.6 `PlatformOptions::quiet_messages_file`, M10.11 the `PlatformFactory` of `run_updater`
    (change 6).
14. **An `exe` module's sources cannot be linked by its tests**: the benchmark harness is the
    library `fv_bench` (M10.4) and the updater's logic sits in `fv_update_native` (M10.11)
    (change 10).

## Lead decisions

1. **New libraries and executables.** Approve `fv_update_native` (`src/update_native`, `KIND core`,
   `DEPS fv_base fv_pyport fv_download fv_archive fv_sql`, plus `fv_log` from M10.11 for
   `updater.log`), `fv_update` gaining `fv_update_native`, `fiorivoce-updater` (`src/updater`,
   `main.cpp` and the version resource only) built with the dynamic CRT and staged with its DLL
   closure instead of a static CRT (change 3), the benchmark library `fv_bench` (`src/bench`,
   `KIND core`) and the developer executable `fiorivoce-bench` (`src/bench_cli`, never staged;
   change 10). No frozen file changes: the root globs the directories.
2. **Update archive and floor.** The archive is `FioriVoce-<ver>-win64.zip` (change 2), the
   manifest `.fiorivoce-update.json`, the sentinel `.fiorivoce-update-complete`, schema 1,
   topology revision 1, architecture `win-x64`, and `minimum_updater_version` (the bridge floor)
   the version of the first release that ships `fiorivoce-updater`. Without a decision M10.1 uses
   `0.1.0`.
3. **Presets (frozen `CMakePresets.json`), before wave 1 ends.** In every test preset whose
   filter excludes `interactive`, change `"exclude": { "label": "interactive" }` to
   `"exclude": { "label": "interactive|perf" }`, and add the test preset
   `{"name": "windows-perf", "configurePreset": "windows", "configuration": "RelWithDebInfo",
   "output": {"outputOnFailure": true}, "execution": {"jobs": 1},
   "filter": {"include": {"label": "perf"}}}`. Until then the perf tests run in the default
   presets (they only assert ten-times ceilings) and `run_perf.py` filters by label.
4. **Settings key for M10.24 (frozen `keys.inc`), before wave 3.** Add
   `{"key": "fv_dictionary_speech_contexts", "kind": "bool", "default": false, "in_table": false}`
   to `tools/gen/fv_settings_keys.json` and regenerate `src/settings/keys.inc`. The default changes
   to true only by the lead after M10.24's measurement.
5. **Running OpenWhisper code for reference numbers (M10.3, M10.4).** Approve running, under
   `ow_isolation.py` with a temporary data root and `check_isolation.py` around each run, nothing
   installed and only 127.0.0.1 contacted: `main.py --workflow-smoke`,
   `scripts/bench_dictation_overhead.py`, `benchmarks/live_preview.py` on the fixture corpus, and
   the Pi sidecar bundle on the already installed Node against a loopback fake provider (as M8.8's
   recorder). Without approval the OpenWhisper column comes from OpenWhisper's committed
   documents only, and the agent-loop budgets are absolute.
6. **Synthetic speech fixture (M10.7, M10.24).** Approve generating speech WAVs offline with
   Windows' built-in SAPI voice into files (never to the speakers) and committing them with their
   OpenWhisper transcripts made through the owner's installed runtime and model, read-only. This
   closes the open item on real-decode parity without committing a human recording.
7. **Dropped benchmark files.** Confirm dropping `test_meeting_product_eval.py` (LLM-judged
   developer evaluation) and `test_audio_dsp_benchmark.py` (denoiser experiments that ship no
   behaviour), and the four product-eval functions of `test_benchmark_contracts.py`.
8. **Release workflows.** Confirm that `qualify-release.yml` and the upload job are written with
   `if: vars.FIORIVOCE_RELEASE_REPO != ''` and never run, and that `test_workflows.py` allows
   `gh release upload` only there; and that the demo's "signed release" is unsigned (no
   certificate), with signing written and skipped.
9. **Sweep splits (change 13).** Confirm M10.26, M10.27 and M10.28 as the second halves of the
   first cut's M10.7, M10.19 and M10.21, and the wave-2 and wave-4 chains that schedule them.

    `HKCU\Software\FioriVoceTest\` may name its own app id and makes `fiorivoce-updater` write
    its failure message to a file instead of a window, which is what lets the demo test run
    unattended as `[platform]`; a production journal is unaffected.
