## Overview

M6 ports a22 (the walkthrough recording model, section-by-section transcription, the PDF, Word
and Markdown documents, the library with Review, write-up versions, recovery and retention, the
AI write-up, the Snap screenshot overlay with annotation, live drawing, and the two-step paste to
an agent), a23 (the Walkthrough tab, the live column, the storyboard, the ready card, the
Walkthroughs side panel, the library dialog and the write-up style dialogs), the walkthrough
runtime of a04 (the walkthrough job inside `TranscriptionRuntime`, snap modes and countdown,
Auto Mode with click capture and live drawing, the board edits), the new `fv_documents`
library, and the installed-agent drivers the write-up needs (change 2). It also finishes the
walkthrough rows that M1, M2 and M4 deferred: the overlay's Snap and Done controls, parking and
stand-in (a07), passive click observation (a06), the Walkthroughs Settings page (a11), the New
write-up style dialog (a13), the tray, window, side panel and controller glue (a01, a03, a09).

**Demo (section 11):** "Record a walkthrough with Snap and live drawing, review the storyboard,
export PDF, Word and Markdown, AI write-up through Claude Code." Concretely, run by the owner on
this machine (it captures the owner's screen, injects a paste and spends the owner's Claude Code
credit, so no worker runs it; amendment 18):

1. Settings > Dictation > Walkthroughs: set the Walkthrough and Screenshot shortcuts, turn "Write
   it up with an AI agent" on with Agent "Claude Code", Default copy "PDF copy". The Walkthrough
   tab shows the same choices in its column.
2. Press the Walkthrough shortcut over a browser. The 296 px column appears at the right edge,
   "Recording 0:03 · 0 shots"; ticks follow the voice. Press Screenshot: every monitor freezes
   under the smoked overlay; drag a region, draw an arrow, a box, a step number and a text label,
   press Enter. The picture flies into the column as "1 · 0:07". Snap ▾ > "Whole screen" takes
   one at once. Turn Auto Mode on before the next walkthrough: a click in the browser is kept
   350 ms later, and a pen stroke on the live toolbar's canvas is kept with its marks. Hold "Hold
   for note" and say "skip the setup part". Press Done.
3. The column says "Writing it up…", the status line "Transcribing section 2 of 3...", then
   "Writing the walkthrough...", then "Writing it up with Claude Code...". The ready card reads
   "Write-up copied", "3 screenshots · 1:12 — paste it into your agent"; the folder
   `%LOCALAPPDATA%\OpenWhisper_CPP\captures\2026-…\` holds `walkthrough.{md,pdf,docx,json}`,
   `write-up.{md,pdf,docx}` and `shot-1..3.png`. Word and a PDF viewer open both documents.
4. The Walkthrough tab shows the storyboard of the newest walkthrough: switch to "As spoken", fix
   a word, switch a screenshot off, drag a row, "Save changes" (PDF, Word and Markdown rebuilt
   off the UI thread); Copy PDF, Copy Markdown, Copy Word; "Redo as" > "Bug report" makes write-up
   version 2 and the version picker reads "Version 2 of 2".
5. Click a chat box and press Ctrl+Shift+F12 (Paste latest walkthrough): the PDF is pasted, then
   800 ms later the agent instructions; the status reads "PDF and instructions pasted; review them
   before sending".

**Rules that apply to every package below** (M0.md's to M5.md's rules, unchanged, plus these):

- A package changes only what its `Owns` line lists, plus its own `tests/<dir>/PARITY.json`
  entries, its case files `tools/parity/cases/<python.module>.py`, its builder file and its
  `tests/golden/`, `tests/fixtures/walkthrough/` and `tests/reference/<widget>/` entries.
  Builders: `tools/parity/builders/a22.py` (Snap) is extended by M6.3, M6.8 and M6.10;
  `a23.py` (walkthrough UI) by M6.5, M6.9, M6.12, M6.15 and M6.16; `a07.py` by M6.4; `a11.py`
  by M6.9; one per wave each.
- Function-level PARITY as in M1.md: each package lists the functions its "Tests to port" names
  (`ported`, `golden`, `dropped`, `other-platform`, or at most 10 % of its own scope `pending`
  with a reason and a finishing package).
- Qt-free code keeps Python's names in snake_case; Qt classes use camelCase with OpenWhisper's
  class names and file stems (section 8.3); every class states its affinity. Qt code writes
  `Q_SIGNALS`, `Q_SLOTS` and `Q_EMIT` (amendment 17). User-visible strings are copied verbatim
  from the cited Python line, typographic characters included: every "…" in a23's strings is the
  single character U+2026 (a23 map, "Added by check"). "OpenWhisper" in copy, window titles,
  document metadata and MIME types becomes `identity().product` (or its lower case): "Spoken notes
  with screenshots, transcribed by OpenWhisper_CPP.", PDF creator "OpenWhisper_CPP", DOCX comments "Made by
  OpenWhisper_CPP", "OpenWhisper_CPP Snap", "OpenWhisper_CPP Walkthrough Drawing", "OpenWhisper_CPP Walkthrough Canvas",
  `application/x-openwhisper-cpp-walkthrough-row`, "restarting OpenWhisper_CPP finishes that", the temporary
  folder prefixes `openwhisper-cpp-walkthrough-` and `openwhisper-cpp-pass-`. No C++ literal spells the
  product (`lint.brand`).
- **Nothing a test does takes over the desktop, reaches beyond this machine or spends the owner's
  credit (amendment 14, lead note 3).** Screen capture goes through a grab seam fed with synthetic
  `QImage`s; window enumeration, window-under-pointer, foreground forcing, capture exclusion, the
  mouse hook, clipboard writes and pastes go through seams with fakes
  (`ui_snap/testing/fake_desktop.h`, `hotkeys/testing/fake_mouse_hook.h`,
  `focus/testing/fake_clipboard.h`, `fake_synthetic_keys.h`). Widgets run on the offscreen
  platform (`QT_QPA_PLATFORM=offscreen`, set by CTest; multi-screen tests use the offscreen
  plugin's screen configuration file). Agent CLIs are M5.7's `fv_fake_agent` copied into a
  temporary folder as `claude.exe`, `codex.exe` and `opencode.exe`, with `USERPROFILE`,
  `CLAUDE_CONFIG_DIR`, `CODEX_HOME` and `XDG_CONFIG_HOME` in the test's temporary folder. Every
  test of the real API (`QScreen::grabWindow`, `SetWindowDisplayAffinity`, `SetForegroundWindow`
  and `AttachThreadInput`, `EnumWindows` over the owner's desktop, the click hook, the real
  clipboard, a real Claude Code run) is written, tagged `[interactive]` and not run; the package
  report lists them.
- **Runtime components (lead note 4).** The document exports need none: PDFs are written with
  `QPdfWriter` and `QTextDocument` (Qt Gui, already deployed), Word files with minizip-ng
  (`archive::ZipWriter`, vcpkg) and hand-written OOXML, Markdown as text. PDFium and ONNX Runtime
  are not loaded by the app in M6. OpenWhisper's own tests read PDFs back with pypdfium2, which
  bundles PDFium (`.venv\Lib\site-packages\pypdfium2_raw\pdfium.dll`, pypdfium2 5.14.0, from
  `requirements-build.txt`), and Word files with python-docx 1.2.0. The C++ tests read Word files
  back with `archive::ZipReader` and pugixml (both linked already); they read PDF text, metadata
  and page sizes through a test-only reader (`tests/documents/support/pdfium_reader.{h,cpp}`,
  M6.7) that loads `pdfium.dll` by path from `OPENWHISPER_CPP_TEST_PDFIUM`, declares the dozen
  `FPDF_*` entry points it calls itself (no vendored header), and `SKIP`s with a message when the
  variable is unset, like the `decode` tests. The checks that must always run use the composer's
  own record of which lines and frames went on which page (M6.7).
- Format with `wsl clang-format --dry-run -Werror` (amendment 3).

## Changes to the cut

Section 11 gives M6 no package table; these choices are this spec's.

1. **`fv_walkthrough` renders through an interface.** The library, the write-up and
   `build_documents` must write PDFs and Word files, which need Qt Gui, while `fv_walkthrough`
   is `core` and `fv_documents` depends on it (section 2.3). M6.1 declares
   `walkthrough::DocumentRenderer` (header only, with a fake); `fv_documents` implements it
   (`documents::QtDocumentRenderer`, M6.7 and M6.14) and the composition installs it with
   `walkthrough::set_document_renderer`. The core and its tests never load Qt; that is also
   Python's rule that startup recovery must not import the Qt renderer (`library.py:121-123`).
2. **The installed-agent drivers come forward from M8.** The write-up runs
   `meeting/agent/installed/core.py:run_reading_task` (Claude Code) and `run_viewing_task` (Codex,
   OpenCode), which need the headless drivers of `drivers.py` and the loopback MCP server of
   `mcp_server.py`. Section 2.3 already places "headless drivers, ACP client, `run_reading_task`"
   in `fv_agents`; M6.2 ports them there, with the loopback MCP server as
   `agents/loopback_mcp.*` (not in `fv_meeting_agent`) so that `fv_agents` does not depend on a
   meeting library; `fv_agents` gains `fv_net`. `InstalledAgentCore` (meeting passes, cadence,
   personas), the meeting tools and agent cleanup stay M8 (amendment 18); M8 reuses the drivers,
   `run_agent_task` and the server.
3. **`WalkthroughRuntime` is a Qt-free UI actor in `fv_walkthrough`** (section 2.4 places a04's
   walkthrough runtime there; principle 2). Everything Qt it touches goes through ports declared
   in `walkthrough/runtime_ports.h` (M6.6): `SnapPort` and `LiveDrawingPort` (implemented in
   `fv_ui_snap` by M6.10), `PanelPort` (by M6.16 over `WalkthroughPanel`), `RecordingPort` (by
   M6.11 over `TranscriptionRuntime` and the `Recorder`), `ClickWatcher` and the mark-shortcut
   family (by M6.16 over M6.4's click observer and `HotkeyManager`). Screenshots cross as
   `walkthrough::ShotImage` (M6.1), implemented over `QImage` by `ui_snap::QImageShot` (M6.8).
   Its timers run on the injected `Executor` and `Clock`, so the 55 shortcut tests replay on a
   `ManualExecutor`.
4. **`WalkthroughPaste` is Qt-free too** (`walkthrough/paste.*`, M6.13), over `focus::ClipboardPort`,
   `focus::SyntheticKeys` and `focus::same_target`; `fv_walkthrough` gains `fv_focus`.
5. **`CaptureDelay` lives in `fv_ui_snap`, not `fv_ui_record`.** `capture_delay.py` paints with the
   Snap chrome and icons and keeps itself out of screenshots (`capture_delay.py:17-19, 179`); the
   live toolbar and the tab embed it, and both already depend on `fv_ui_snap`.
6. **`fv_ui_snap` is `KIND ui`, not a feature.** It registers nothing: the walkthrough feature
   provides its ports as services. `fv_ui_walkthrough` is created `KIND ui` by M6.5 and becomes
   `KIND feature` (`fv_feature(ID walkthrough CLASS fv::WalkthroughFeature)`) in M6.16.
7. **The a23 column model stays beside its widget.** `WalkthroughColumn` (Qt-free) is
   `ui_walkthrough/walkthrough_column.{h,cpp}` rather than in `src/walkthrough` (section 2.4),
   because M6.1 owns `src/walkthrough` in wave 1 and the column ships in the same wave; it
   includes no Qt header and has its own Qt-free test file.
8. **The controller glue lives in the feature** (section 8.5): `ui_qt/ui_controller.py:1067-1332`
   and the walkthrough-library gate of `application_controller.py:792-820` become
   `ui_walkthrough/walkthrough_presenter.*` (M6.16). Only two seams of `src/ui_controller` (audio
   levels and the error-time dismissal) and the shell's walkthrough lines are edited there.
9. **Sections decode from WAV clips, as in Python.** `transcribe_sections` writes
   `section-<i>.wav` and `note-<i>.wav` into a temporary folder and decodes each through
   `speech::decode_file` (swresample windows, section 5.2), so a C++ and a Python decode of the
   same recording receive the same samples. Decoding spans from memory is an M10 performance item.
10. **The New write-up style dialog** (`ui_qt/dialogs/new_style_dialog.py`, a13, A13-50) is
    `ui_walkthrough/new_style_dialog.*` (M6.15), and the redo-with-prompt dialog
    `ui_walkthrough/write_up_prompt_dialog.*` (M6.12), next to their only callers.
11. **Local stylesheets are resources applied per widget.** The `_STYLE` strings of
    `walkthrough_tab.py:125-324`, `walkthrough_review.py:95-299`, `past_walkthroughs.py:303-369`
    become `src/ui_walkthrough/resources/{walkthrough_tab,walkthrough_review,past_walkthroughs}.qss`,
    loaded from `:/ui_walkthrough/` and applied through `fv::ui::setLocalStyleSheet`. None is
    named `ui_walkthrough.qss`, which the theme pipeline would append to the application sheet.

## Contract gaps

What the contracts in the tree (or in the M1 to M5 specs) lack, and the package that adds it under
amendment 10:

1. `archive::ZipWriter` (M3.1) writes Zip64 extra fields on every entry; a `.docx` is written
   without them, as python-docx's `zipfile` does: M6.14 adds `ZipWriter::Options{bool zip64}`.
2. `focus::ClipboardPort` and `clipboard::TemporaryClipboard` cannot say whether a given auto-paste
   marker is still on the clipboard (`walkthrough_paste.py` compares the MIME bytes): M6.13 takes
   the check as an injected function; M6.16 adds `TemporaryClipboard::markerPresent`.
3. M2.6's `MouseHookSource` has no passive click observer (A06-15): M6.4 adds `ClickObserver`.
4. M2.17's `HotkeysPage` builds standard shortcut rows only on its own page; the Walkthroughs page
   needs the same rows bound to the same capture, conflicts and reset: M6.9 adds
   `HotkeysPage::shortcutRow`.
5. `TranscriptionRuntime` (M1.14) has no walkthrough job, `walkthrough_written_up`, `writing_up` or
   `cancel_write_up`: M6.11.
6. `WaveformOverlay` (M1.8, M2.12) declares the Snap and Done signals but has no
   `setWalkthroughControls`, `park`, `unpark` or `setStandIn`: M6.4.
7. `fv_agents` (M5.6, M5.7) has no pass drivers, loopback MCP server or one-off tasks, and
   `fv_fake_agent` no `stream-json` output or `--image` handling: M6.2.
8. `MainWindow` (M1.21) has no `showWalkthrough(folder)` or Walkthroughs side-panel pick: M6.16.
9. `fv_walkthrough` is new; its renderer and runtime ports are declared ahead of their
   implementations (changes 1 and 3): M6.1 (`renderer.h`, `shot_image.h`), M6.6
   (`runtime_ports.h`).

### Traps

- The cut search runs on the int16 frames as recorded, energy summed over channels with prefix
  sums; `fv::read_wav` averages to float and would change stereo results (a22 "Engine-specific
  code"). Window `int(0.1*rate)`, step `width//2`, ties to the window nearest the target
  (`lexsort((distance, energy))`), keep the target unless min energy ≤ 0.5 × the energy of the
  window nearest it (`sections.py:67-86`); cuts never decrease nor pass the next mark
  (`:43-64`); a clip shorter than 0.25 s is `Clip{nullopt, duration}` and is not decoded.
- `wave` writes clips at the recording's rate and channel count, 16-bit; a non-16-bit input raises
  "expected 16-bit audio, got N-bit" and `transcribe_sections` then decodes the whole file into
  section 0 with `before_each(1, 1)` and no notes (`finish.py:44-50`). `OSError`, `ValueError` and
  `wave.Error` all take that fallback: catch the C++ equivalents only.
- `add_shot` copies the image before queuing (`session.py:373`); a delete is queued after its own
  write (`:318-319`); a failed write deletes the partial file, emits `save_failed(number)` on the
  writer thread and the shot leaves the board like a removed one; `storyboard()` waits up to
  30 s per save, a timeout counts as unwritten.
- `move_shot` refuses moving into or over the trailing section (`:340`); `_remove` prepends the
  removed pieces to the next section; `undo_last` takes the largest kept index still on the board.
- `draft.json` v1 keeps `started_at` naive (`isoformat()` without offset), `journal_id` "" when
  none, shots in kept order, open notes as `null`; the manifest's `started_at` has the local
  offset at seconds (`astimezone().isoformat(timespec="seconds")`). Floats are Python `repr`.
- `discard()` deletes only the fixed names and the shots, then `rmdir` (kept quietly if
  `write-up-N.*` or temp files remain); `end()` lets the writer finish without waiting.
- `_when` uses English day and month names whatever the locale; `clock` floors and clamps
  negatives; the Markdown header is `_<details>. <about>_` and the file ends in one `\n`, LF only.
- `_image_target`: relative POSIX path inside the folder, wrapped in `<>` when it has whitespace
  or parentheses; an absolute target is always `<…>` with native separators (`document.py:292-303`).
- Paths come from `path_from_utf8` / `path_to_utf8`, never `path.string()`.

  no document"; `OSError`/`ValueError` while writing "could not write its documents: …".
- `document_text` keeps only images whose basename (after `\` to `/`) is one of our shot names
  and rewrites them to the bare name; the look block keys are normalised (lower case, `[\s_-]+` to
  a space, colour to color).
- `local_file` refuses names with separators, a symlinked folder or file, and non-regular files;
  `read_json` refuses symlinks and files over 8 MiB; `delete_entry` refuses symlinks, folder names
  not matching `_FOLDER`, and any unexpected entry including sub-directories ("Folder contains
  extra files; remove it in your file manager").

  as 0; `prune` touches only finished folders (manifest, no draft) by the manifest's mtime.
- `recovery_session` requires `audio.wav` as a safe local file and version 1, skips unreadable
  PNGs (a PNG signature and IHDR check, since the core has no image reader: say so in the report),
  requires ordered notes and non-decreasing shot times; `attach_recovered_audio` needs exactly one
  `recording_*-recovered-<32 lowercase hex>.wav` and ignores per-folder errors.
- Styles: id = 12 hex characters of a random UUID; the starters are returned, not saved, until
  the key exists; deleting a starter materialises the rest; the error texts are verbatim

### Traps

  stand-in, and minimize to tray when ticked and the window is visible (`:1134-1146`); the column

  the write-up; a cancelled or failed job dismisses it unless a write-up is running.

  {exc}"; a paste in progress: "Walkthrough saved; another walkthrough paste is in progress";
  warnings "Write-up failed: …" and "{n} screenshot(s) couldn't be saved" joined by ". ".
